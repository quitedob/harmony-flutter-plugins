# 测试分析 Skill

## 概述

基于 IBO（Input-Behavior-Output）模型对 Flutter/RN/原生库鸿蒙化适配进行结构化测试分析，生成测试点和测试分析报告。

**适用范围**：阶段 2 - 测试分析  
**输入**：需求解析结果（00-requirement.json）或 PRD 文件  
**输出**：测试分析报告（Markdown）、测试点汇总（JSON）

---

## 输入参数

| 参数 | 必填 | 说明 |
|------|------|------|
| `prd_path` | 否 | PRD 文件路径（支持 .md, .xlsx, .json），当需求解析结果不存在时必需 |
| `output_dir` | 否 | 输出目录（默认为 `.ohos-adaptation`） |
| `plugin_type` | 否 | 插件类型（platform_interaction, business_feature, ui_component, architecture_tool, ffi） |

---

## 输出文件

| 文件 | 说明 |
|------|------|
| `{output_dir}/02-test-analysis-report.md` | 测试分析报告（Markdown） |
| `{output_dir}/02-test-points.json` | 测试点汇总（JSON，Schema 见 `assets/test-points-schema.json`） |

---

## 执行步骤

### 步骤 1：读取需求解析结果（优先）

1. 检查 `{output_dir}/00-requirement.json` 是否存在
   - 存在：读取 JSON 获取功能模块、API 接口、优先级等信息
   - 不存在：检查 `00-requirement-report.md` 或直接读取 PRD 文件

2. **从需求解析结果中获取**：
   - 插件基本信息、功能模块列表、API 接口列表、权限需求、使用场景

> **注意**：优先使用需求解析结果，只有当需求解析结果不存在时才读取 PRD 文件。

### 步骤 2：逐模块进行 IBO 分析

对每个功能模块执行：

1. **识别输入特征**：分析 API 参数类型，识别特殊输入
2. **识别行为特征**：分析行为关键词，识别状态转换、异步行为等
3. **识别输出特征**：分析返回值类型，识别特殊输出
4. **生成测试点**：基于 IBO 分析生成测试点，指定级别（L0-L3），标注覆盖 API

> **详细说明**：见 `references/ibo-model.md`（IBO 模型详解）、`references/test-point-generation.md`（测试点生成规则）。

### 步骤 7：平台无关性验证

**核心原则**：测试分析是针对三方插件鸿蒙化后的测试分析，测试点中不应体现源平台（Android、iOS）的特定内容。

**必须验证的内容**：
- [ ] 测试点描述中不包含 "Android"、"iOS"、"源平台" 等平台特定词汇
- [ ] 测试点描述中不包含源平台特有的版本号（如 "Android 12+"、"iOS 15+"）
- [ ] 测试点描述中不包含源平台特有的 API 名称（如 "BLUETOOTH_CONNECT"、"UIImagePickerController"）
- [ ] 权限、功能等描述应使用鸿蒙平台的通用术语

**允许的例外情况**：
- 插件基本信息中的"已支持平台"可以如实记录源平台信息（用于背景说明）
- 风险识别部分可以提及"源平台 X 与鸿蒙平台差异大，需要适配"（作为风险提示）
- 插件简介中可以描述"通过封装 Android/iOS API 实现 XX 功能"（作为技术背景）

**验证失败处理**：
- 发现测试点中包含源平台特定内容，必须重新生成测试点
- 将源平台特定描述转换为鸿蒙平台的通用描述

**转化示例**：

| 源描述（错误） | 转化后（正确） |
|--------------|--------------|
| "Android 12+ 新权限模型行为" | "鸿蒙权限模型行为" 或 "新版权限模型行为" |
| "Android 12+ 正确处理 BLUETOOTH_CONNECT/SCAN 权限请求" | "正确处理蓝牙连接/扫描权限请求" |
| "如'Android 13'" | "如'HarmonyOS NEXT'" 或 "如'API 23'" |

## 核心方法论

### IBO 模型

采用 **IBO（Input-Behavior-Output）模型** 进行结构化测试分析：

| 维度 | 分析内容 | 测试方法 |
|------|----------|----------|
| **Input（输入）** | 输入参数的类型和特征 | 等价类划分、边界值分析、空值测试 |
| **Behavior（行为）** | 功能行为的特征 | 状态迁移测试、因果图与判定表、并发测试 |
| **Output（输出）** | 输出数据的类型和特征 | 空集合测试、边界值分析、格式验证 |

> **详细表格和示例**：见 `references/ibo-model.md`。

### 测试点级别划分

| 级别 | 定义 | 适用场景 |
|------|------|----------|
| L0 | 核心功能的正常流程 | P0 模块正常流程 |
| L1 | 核心功能异常/边界 + P1 正常流程 | P0 异常/边界 + P1 正常 |
| L2 | P1 异常/边界 + P2 正常流程 | P1 异常/边界 + P2 正常 |
| L3 | P2 异常/边界 | P2 异常/边界 |

**级别判定规则**：P0+ 正常=L0 | P0+ 异常=L1 | P1+ 正常=L1 | P1+ 异常=L2 | P2+ 正常=L2 | P2+ 异常=L3

> **级别分布参考**：见 `references/test-point-generation.md`。

## 插件类型识别

根据插件的功能描述和 API 特征，自动识别插件类型。

### 插件类型分类（简表）

| 类型 | 特征关键词 | 测试重点 |
|------|------------|---------|
| **platform_interaction** | 相机、蓝牙、传感器、屏幕、原生 API | 系统 API 调用、权限处理、平台兼容性 |
| **business_feature** | 支付、地图、推送、OCR、第三方 SDK | 业务流程、错误处理、数据安全 |
| **ui_component** | 组件、UI、渲染、Widget、弹窗 | UI 渲染、交互体验、动画效果 |
| **architecture_tool** | 工具、封装、路由、状态管理 | 功能正确性、性能、接口兼容性 |
| **ffi** | FFI、原生库、.so、动态库 | 原生库加载、内存安全、接口调用 |

### 类型识别优先级

1. FFI 类（特征最明显）→ 2. 平台交互类 → 3. 业务功能类 → 4. UI 组件类 → 5. 架构与工具类（兜底）

> **详细分类和关键词**：见 `references/plugin-types.md`。

## 边界情况处理

| 情况 | 处理方式 |
|------|---------|
| 需求解析结果不存在 | 读取 PRD 文件并提取功能模块和 API 信息 |
| PRD 章节缺失 | 从已有内容中推断，无法推断的记录为警告 |
| 模块优先级不明确 | 根据功能重要性判断（核心功能=P0，辅助功能=P1/P2） |
| 插件类型不明确 | 使用兜底类型 architecture_tool |
| 字段值不确定 | 使用 null 标记，不猜测 |
