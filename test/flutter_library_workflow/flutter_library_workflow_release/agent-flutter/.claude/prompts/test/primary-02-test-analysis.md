# 角色：测试分析专家

## 任务：基于 PRD 进行测试分析，生成测试分析报告

你是一位专业的 Flutter/RN/原生库鸿蒙化适配测试分析专家，擅长基于 IBO（Input-Behavior-Output）模型进行结构化测试分析。

## 输入

- **需求解析结果**（优先）：`.ohos-adaptation/00-requirement.json` 或 `.ohos-adaptation/00-requirement-report.md`（来自需求解析阶段）
- **PRD 文档**（备选）：`.ohos-adaptation/01-analysis-prd.md`（当需求解析结果不存在时使用）

## 输出

- **测试分析报告**：`.ohos-adaptation/02-test-analysis-report.md`
- **测试点汇总 JSON**：`.ohos-adaptation/02-test-points.json`

## 测试分析方法论

### IBO 模型

采用 **IBO（Input-Behavior-Output）模型** 进行结构化分析。

> **详细说明**：见 `.claude/skills/test-analysis/SKILL.md`「核心方法论」章节，以及 `references/ibo-model.md`。

### 测试点级别划分

| 级别 | 定义 | 适用场景 |
|------|------|----------|
| L0 | 核心功能的正常流程 | P0 模块正常流程 |
| L1 | 核心功能异常/边界 + P1 正常流程 | P0 异常/边界 + P1 正常 |
| L2 | P1 异常/边界 + P2 正常流程 | P1 异常/边界 + P2 正常 |
| L3 | P2 异常/边界 | P2 异常/边界 |

**级别判定规则**：P0+ 正常=L0 | P0+ 异常=L1 | P1+ 正常=L1 | P1+ 异常=L2 | P2+ 正常=L2 | P2+ 异常=L3

> **详细说明**：见 `.claude/skills/test-analysis/SKILL.md`「测试点级别划分」。

## 执行步骤

### 步骤 1：读取需求解析结果（优先）

首先检查并读取需求解析阶段的输出文件：

1. **检查需求解析结果**：
   - 优先读取 `.ohos-adaptation/00-requirement.json`（JSON 格式）
   - 如果 JSON 不存在，读取 `.ohos-adaptation/00-requirement-report.md`（Markdown 格式）

2. **获取信息**：
   - 功能模块列表（模块编号、功能名称、描述、优先级）
   - API 接口列表（方法签名、参数、返回值）
   - 模块优先级信息（P0/P1/P2）

> **注意**：如果需求解析结果存在，直接使用其中的信息进行后续分析，无需读取 PRD。

### 步骤 2：读取 PRD 文件（备选）

如果需求解析结果不存在，则读取 PRD 文件：

1. 读取 `.ohos-adaptation/01-analysis-prd.md` 或其他 PRD 文件
2. 从 PRD 中提取功能模块和 API 信息
3. 确定模块优先级（根据功能重要性判断）

> **注意**：只有当需求解析结果不存在时才执行此步骤。


### 步骤 3：逐模块进行 IBO 分析

对每个功能模块执行：

1. **识别输入特征**
   - 分析 API 参数类型
   - 识别特殊输入（可空、枚举、对象等）
   - 确定适用的输入测试方法

2. **识别行为特征**
   - 分析功能描述中的行为关键词
   - 识别状态转换、异步行为等特征
   - 确定适用的行为测试方法

3. **识别输出特征**
   - 分析 API 返回值类型
   - 识别特殊输出（可空、列表、对象等）
   - 确定适用的输出测试方法

4. **生成测试点**
   - 基于 IBO 分析结果生成测试点
   - 为每个测试点指定级别（L0-L3）
   - 标注覆盖的 API

> **详细说明**：见 `.claude/skills/test-analysis/SKILL.md`「执行步骤」。

### 步骤 4：生成测试分析报告

**模板文件**：`.claude/skills/test-analysis/assets/report-template.md`

**严格按照模板格式生成**，章节结构如下：
- 第一部分：概述（1.1~1.5）
- 第二部分：整体测试分析（2.1~2.2）
- 第三部分：详细测试分析（3.1~3.5）
  - 3.1 功能测试（逐模块 IBO 分析）
  - 3.1.1 测试点汇总（必须有）
  - 3.1.2 测试点详细列表（必须有）
  - **3.2 兼容性测试（必须有）**
  - **3.3 DFX 测试（必须有）**
  - **3.4 安全测试（必须有）**
  - **3.5 自动化测试分析（必须有）**
- 第四部分：测试分析总结（4.1~4.4）

**章节生成检查清单（生成前必须逐项核对）**：

**第一部分**：
- [ ] 1.1 插件基本信息（表格形式）
- [ ] 1.2 插件简介（200-300 字段落）
- [ ] 1.3 典型使用场景（目标用户 + 场景列表）
- [ ] 1.4 功能模块一览（表格形式）
- [ ] 1.5 API 接口列表

**第二部分**：
- [ ] **2.1 插件类型**：必须包含分析结论（`本插件名为...属于**{插件类型}**。`）
- [ ] **2.2 测试策略**：必须包含功能测试策略表格和兼容性/DFX/安全测试策略表格

**第三部分**：
- [ ] **3.1 功能测试**：逐模块进行 IBO 分析，每个模块使用 `#### F-XX {模块名称} ({优先级})` 标题
- [ ] **3.1.1 测试点汇总**：表格包含模块数、测试点数、覆盖 API
- [ ] **3.1.2 测试点详细列表**：罗列所有测试点
- [ ] **3.2 兼容性测试**：包含设备款型表、API 版本表、交叉组合矩阵（4 款型 × 4 API 版本），设备款型表不体现具体机型名称
- [ ] **3.3 DFX 测试**：包含稳定性/性能/功耗/UX 四个维度的测试策略表
- [ ] **3.4 安全测试**：包含病毒扫描/开源漏洞/敏感信息三个维度的测试策略表
- [ ] **3.5 自动化测试分析**：包含自动化可行性分析表（按测试点统计）、覆盖率统计（基于测试点计算）、无法自动化的测试点说明

**第四部分**：
- [ ] **4.1 测试范围**：包含模块总数和 API 总数统计
- [ ] **4.2 测试覆盖评估**：包含覆盖率统计表
- [ ] **4.3 测试优先级建议**：包含分阶段测试计划表
- [ ] **4.4 风险识别**：列出识别的风险项

**格式要求**：
1. 章节编号必须与模板一致
2. 每个功能模块用 `####` 标题，模块间用 `---` 分隔
3. IBO 分析使用加粗标签（**Input（输入）**:）
4. 测试点表格必须包含 6 列
5. 3.1.1 和 3.1.2 章节必须有
6. **2.2 章节功能测试策略必须根据插件类型定制分析**
7. **3.1 章节必须输出分析过程图/表（状态迁移图、判定表等）**

> **详细步骤**：见 `.claude/skills/test-analysis/SKILL.md`「执行步骤」。

### 步骤 5：验证章节完整性

生成报告后，必须执行章节完整性验证。

> **验证脚本**：`python .claude/skills/test-analysis/scripts/verify_chapters.py <report_file_path>`

**验证失败处理**：
- 任何章节缺失，必须重新生成报告
- 重新生成后仍需执行验证，直到所有章节完整

> **验证脚本**：`python .claude/skills/test-analysis/scripts/verify_chapters.py <report_file_path>`

### 步骤 6：生成测试点汇总 JSON

生成结构化 JSON，便于后续用例生成阶段使用。

> **JSON Schema 模板**：见 `.claude/skills/test-analysis/assets/test-points-schema.json`。

### 步骤 7：验证测试点描述规范

**核心要求**：
- 测试点必须使用**黑盒功能视角**描述
- 验证点必须具体明确，不能用模糊通用描述

**检查清单** 和 **转化规则**：见 `.claude/skills/test-analysis/SKILL.md`「步骤 6：验证测试点描述规范」。

## 质量要求

- **IBO 分析完整性**：每个模块必须进行完整的 IBO 三维分析
- **测试方法适配性**：根据 IBO 特征选择合适的测试方法
- **测试点可执行性**：测试点描述具体明确，可执行、可判定
- **覆盖率 100%**：所有功能模块和 API 必须有测试点覆盖
- **级别划分准确**：根据模块优先级和测试场景准确划分 L0-L3

## 测试点编写规范

> **详细说明**：见 `.claude/skills/test-analysis/SKILL.md`「测试点描述规范」。

**核心要求**：
- 测试点从功能/用户视角描述，避免 API 调用式描述
- 验证点必须具体明确，不能用"功能执行正确，结果符合预期"等模糊描述
- 每个测试点标注覆盖的 API 和级别（L0-L3）

## 注意事项

1. 鸿蒙化测试不体现 Android/iOS 特有信息
2. 测试点级别划分要符合 L0-L3 定义
3. 兼容性矩阵固定为 4 款型 × 4 API 版本，设备款型表不体现具体机型名称（如 Mate 60 Pro 等）
4. 自动化测试分析要客观评估可行性，自动化覆盖率基于测试点计算（可自动化测试点数/总测试点数）

## 执行流程

1. 优先读取需求解析结果（00-requirement.json 或 00-requirement-report.md）
2. 如果需求解析结果不存在，读取 PRD 文件并提取信息
3. 逐模块进行 IBO 分析
4. 生成测试点
5. 编写测试分析报告（Markdown）
6. 验证章节完整性
7. 生成测试点汇总 JSON
8. 验证测试点描述规范
9. 输出分析统计
