# Android → HarmonyOS UI 保真复刻流程

本 Skill 通过一套**可逐项核验的确定性流程**，确保 HarmonyOS UI 与 Android UI 保持一致。

整个流程由五个相互衔接、**每一步都可观察、可核验**的强制环节组成：
**⓪ 清点源** → **① 抽规格** → **② 实现 + 硬性 lookup** → **③ 逐行 diff + 证据** → **④ 诚实落盘**。

---

## 一、三条基本规则（验收标准，违反即返工）

1. **不简化 / 不丢能力**：Android 可配置的每一个尺寸、颜色、状态、字形、形状和动画，ArkUI 都必须**等量还原并保持可配置**，不得写死。Android 的**可配置样式属性、Adapter 的全部公开方法、可注册类型（`registerXxxType`）和工厂注册点**，HAR 必须**逐项等量保留**，数量与签名保持一致。**禁止使用一个通用入口合并多个具名公开方法**，除非 Android 原实现本身就是通用入口。
2. **不丢状态**：常态、按下、选中、禁用和聚焦状态必须完整保留。Android selector 中有几个 item，ArkUI 就必须有几个对应分支，不能遗漏。
3. **不做未说明的降级**：渐变不能简化为纯色，异形不能简化为矩形，斜体不能丢失，圆角、阴影、描边和 9-patch 必须复刻。**没有现成的一对一能力时，应通过等价实现补齐视觉和交互，不能跳过或直接简化。** 如果确实无法完全还原，应如实写入差距清单（第五节），不得隐瞒，也不得宣称“完全一致”。

---

## 二、“一致”的定义 —— 保真维度（核验范围，不是映射答案表）

“一致”不是“看起来差不多”，而是下列**每一个实际涉及的维度**都与 Android 源码一致。任何维度存在偏差，都属于真实缺陷。本节用于说明**需要对齐哪些维度**，而不是规定**具体应映射成什么**。

- **D1 结构**：层级、容器类型、排列方向、嵌套关系、子层 z 序，以及相对布局或约束布局中的**每一条对齐关系**。遗漏任何关键关系都可能导致整个界面布局错误。
- **D2 尺寸**：宽高、padding、margin、间距、权重、min/max。数值需要在单位换算后实现**视觉等价**，而不是简单保持数字相同。
- **D3 对齐**：主轴对齐、交叉轴对齐、自身对齐和文本对齐。
- **D4 颜色**：背景色、文字色、边框色和图标色，包括 alpha，**以及每个状态对应的颜色**。
- **D5 状态**：常态、按下、选中、禁用和聚焦状态的样式差异都要完整还原。
- **D6 形状**：圆角（包括逐角设置）、异形裁剪、描边（包括虚线）、阴影/elevation 和 9-patch 拉伸区域。
- **D7 渐变**：渐变类型（线性、径向、扫描）、方向或角度基准，以及每个色标及其位置。
- **D8 文本**：文本的**每一个可观察视觉维度**，包括度量（字号、行高、字距）、字形（字重、**斜体是独立于字重的维度，容易遗漏**；Compose 中对应 `Text` 的 `fontStyle=FontStyle.Italic`，不能只设置 `fontWeight`）、装饰（下划线、删除线、阴影）、字族、截断方式（行数、省略）和方向。
- **D9 图片**：缩放和裁剪方式必须与 scaleType 一致。注意 fitXY 非等比、fitCenter 等比、centerCrop 和 centerInside 的语义不同；同时还要还原圆形/圆角、占位图和着色/tint。Compose 中 `Image` 的 `contentScale` 对应这一维度，`colorFilter=ColorFilter.tint` 对应着色。
- **D10 文本能力**：可点击链接、富文本、Span（包括非颜色 Span），以及文字和图标的组合。
- **D11 列表**：数据源语义、增删改通知的**粒度**（精确到 insert/remove/change/move，不能一律使用整体 reload，因为整体 reload 会丢失动画并降低性能）、分割线、加载更多、多 viewType、sticky header，以及 **Adapter 的全部公开方法**。Compose 的 `LazyColumn` 列表 API 也不能删减，通知粒度不能降低。
- **D12 自定义绘制**：自绘内容（onDraw）、自定义测量与布局（onMeasure/onLayout），以及叠加绘制或替换绘制。
- **D13 交互**：点击、长按、拖动、缩放、旋转、快速滑动、事件分发与冲突、按键处理。**焦点必须使用真实的 focus/blur 事件，不能用定时器近似处理。** 一个手势要还原它的完整过程，不只是手指移动时的变化，还包括手势开始时的初始化，以及手势结束时自动执行的步骤（例如校正、回弹、归位、超出边界后的调整）。只还原移动过程、漏掉开始或结束时的处理，属于未完成。
- **D14 动画转场**：属性动画、出入场动画、页面转场、共享元素转场、模态转场和帧动画。曲线与时长需要对应，元素增删应使用 transition。
- **D15 弹窗提示**：对话框、菜单、底部面板、选择器、Toast 和 Snackbar 的形态与按钮。
- **D16 可见性**：需要区分并还原 GONE（不占位）和 INVISIBLE（占位但隐藏）。Compose 中，条件 `if` 不渲染表示不占位，`alpha` 设为 0 表示占位但隐藏。
- **D17 主题响应**：深色资源完整，颜色通过资源引用而不是写死，同时处理响应式断点和折叠屏。
- **D18 扩展点**：可配置样式属性、Adapter 公开方法和可注册类型必须在 HAR 中**等量保留**，签名与语义保持一致。Compose 的 `@Composable` 参数及默认值、slot lambda、`CompositionLocal` 和回调也要等量保留。

> D1–D18 主要检查静态视觉值是否正确。D19–D21 分别检查运行时状态是否真正连接到渲染、需要的组件或变换是否实际实现，以及函数行为是否与名称和源语义一致。这些问题通常来自 Android 与 ArkUI 编程方式的差异，无法仅通过静态视觉值发现，因此单独列出。

- **D19 状态→渲染绑定**：运行时会变化的视觉属性（变换、可见性、选中状态、数据驱动内容），其驱动状态**必须使用响应式载体**（@State/@Link/@Prop/@Observed）或通过画布显式调用 `redraw()`。Android 中“修改字段后调用 `invalidate` 重绘”的命令式写法，在声明式 ArkUI 中不能直接生效；如果只修改字段而没有建立响应式关系，代码可能不报错，但界面不会更新。
- **D20 自定义 View 实体化 / 变换实体化**：每个 Android `extends View/ViewGroup` 且包含 onDraw/onMeasure/onTouch 的类，都必须对应**一个实际交付的 ArkUI 自绘组件**，不能降级为 Text 或系统组件占位。回调没有调用方属于无效代码，也应视为缺陷，不能仅因符号存在就判定为 PASS。**如果 Android 源码通过 Matrix（pivot/post-concat）或 onDraw 实现几何变换（图像变换、裁剪、缩放映射、像素几何），ArkUI 实现必须使用显式变换模型驱动 Canvas 自绘，具体 API 需要自行 lookup。仅使用 `.scale()`、`.rotate()` 或 `.translate()` 等声明式修饰符不能直接视为等价实现，因为这些修饰符通常围绕组件中心并使用固定组合顺序，无法表达任意 pivot 或 post-concat，可能造成几何结果错误。** 实现这类功能时，应先把原变换模型确定下来（单位、坐标原点、轴心、组合顺序、映射方向），用它驱动一个自绘画面并在数据变化时主动重绘，再决定具体怎么画；不要先选了修饰符再倒推算法。验证不能只看静止状态或能否编译：要取一个有代表性的输入（例如经过平移、缩放、旋转之后的某个点或某块区域），按原算法算出它应该出现的位置，再确认实现把它放到了同一位置。静止时看起来正常、能编译通过，都不能作为变换正确的依据。
- **D21 名实相符**：函数行为必须与其**名称和源语义一致，包括写入位置、通知和持久化等副作用**。源码中出现“简化、mock、TODO、暂时、写死”等内容，都应视为缺陷，不能作为完成结果。**搜索这些标记词是必要检查，但仅靠搜索并不充分。即使没有标记词，核心操作如果返回虚构数据、固定值，或没有执行真实计算（例如 `crop()` 没有进行裁剪却返回固定尺寸），同样属于 GAP。必须逐个检查核心函数体，确认它确实完成了函数名称所表示的行为。** 被移植的工具函数和数学计算也要按原公式核对，不能只看它返回了一个形状合理的值。一个算错但看起来合理的实现（例如本应返回边长却返回了外接框的宽高）同样能编译，也不容易一眼看出，必须回到源码公式逐项确认。

> **以上列出的常见问题（斜体、渐变、异形、Snackbar、reload 等）只是高频示例，并不是完整清单。** Android 源码中存在但本文未单独列出的视觉属性，例如字距、blendMode、RTL/镜像、字体 fallback 和 baseline，也必须按对应维度逐项核对，不能因为本文未点名就默认省略。

## 三、工作闭环（每个界面/组件严格按五步执行，不得跳过）

### ⓪ 清点源 INVENTORY —— 先判断范式，再完整清点源内容

**先判断 Android UI 范式**，以确定需要读取哪些源码。项目可能使用以下任一种范式，也可能混合使用：

- **View / XML 体系**（传统）：读取 `res/layout/*.xml`、自定义 `View`（`.java/.kt` 中的 onDraw/onMeasure）、`attrs.xml`、`styles.xml`、`themes.xml`、全部相关 `res/drawable/*`（shape/selector/gradient/layer-list/ripple/9-patch/vector）、`res/color/*`（ColorStateList）和 `values-night/` 深色资源。
- **Jetpack Compose**（声明式，**没有 XML/drawable/Adapter，UI 全部位于 Kotlin 的 `@Composable` 中**）：读取每个 `@Composable` 函数及其参数和默认值；读取 **`Text`/`BasicText` 的样式参数**（`fontStyle=FontStyle.Italic`、`fontWeight`、`textDecoration`、`maxLines` 和 `overflow=TextOverflow.Ellipsis`；富文本或可点击链接使用 `buildAnnotatedString`/`AnnotatedString`、`LinkAnnotation` 或 `ClickableText`）；读取 **`Image`/`Icon`/`AsyncImage` 的构造参数**（`painter`、`contentScale=ContentScale.*`，对应 scaleType；`colorFilter=ColorFilter.tint(...)` 和 `alpha`）；读取 `Modifier` 链（`.background/.border/.clip`，包括 `GenericShape` 异形；`.padding/.size` 和 `Brush.linear/radial/sweepGradient`）；读取状态（`remember`、`mutableStateOf`、`derivedStateOf`、状态提升）；读取 `LazyColumn`、`LazyRow`、`LazyVerticalGrid` 及 StaggeredGrid 的 `items`、`key`、`contentType` 和 item lambda；读取 `Canvas`、`Modifier.drawBehind`、`drawWithContent` 自绘；读取 `pointerInput`、`clickable`、`detectXxxGestures` 手势；读取 `animate*AsState`、`AnimatedVisibility`、`updateTransition` 动画；读取主题（`MaterialTheme.colorScheme/typography/shapes`、自定义 theme、`isSystemInDarkTheme()`）；读取扩展点（slot `content: @Composable () -> Unit`、尾随 lambda、`CompositionLocal`、回调 lambda、DSL/builder）。
- **互操作（interop）**：`ComposeView` 表示在 View 中嵌入 Compose，`AndroidView` 表示在 Compose 中嵌入 View。**两种范式都需要完整清点，不能只检查其中一部分。**

> Compose 与 ArkUI 都采用声明式、状态驱动和属性/Modifier 链式写法，映射通常比 View 体系更直接；但**三条基本规则、D1–D21 维度和五步流程仍然必须完整执行**。差别只在于源码中的事实采用了不同表达形式，需要核对的维度并没有变化，具体 ArkUI 实现方式仍由执行者判断。Compose 场景需要特别注意：状态与 UI 的重组关系不能简化为静态值；`Modifier` 的顺序会影响视觉结果；slot、`CompositionLocal` 和回调 lambda 都属于扩展点（D18），必须等量暴露；颜色应使用 theme token，不能写死（D17）。

然后**逐项枚举**源码内容，不根据“Demo 是否使用”进行删减，并整理成一张**清册**。每一项必须标明去向，只能是“进入规格表”或“明确判定为无视觉影响并说明理由”，不允许省略。按实际使用的 UI 范式逐项列出：
- **View 体系**：每个 drawable 文件、每个 selector item、每个 values-night 同名 key、每个自定义 attr、每个 public/protected 方法签名、每个 registerXxxType 或工厂注册点、每个 Adapter 公开方法/viewType/回调、**每个 `extends View/ViewGroup` 自定义类（通过 grep 完整找出，去向只能是“→ 自绘组件”，不能使用文字替代）（D20）**，以及**每处 `invalidate`、`postInvalidate`、`notifyXxx`（表示运行时会变化的视觉，需要记录其驱动来源）（D19）**。
- **Compose**：每个 `@Composable` 及其参数和默认值、每个 `Text` 的 `fontStyle`/`textDecoration`/`overflow`、每个 `AnnotatedString` 的样式和可点击 span、每个 `Image`/`Icon` 的 `contentScale`/`colorFilter`、每条产生视觉效果的 `Modifier` 调用、每个状态字段、每个 `LazyColumn` 的 item 类型/`key`/item lambda、每个 slot/`CompositionLocal`/回调 lambda，以及每个对外 `@Composable`、public 函数和 DSL 入口。

| Android 源元素（按上面对应范式逐个列出） | 类别 | 去向：→规格表第 N 行 / 明确判定无视觉影响（附理由） |
|---|---|---|

这一步用于避免遗漏。**如果某项没有写入规格表，后续逐行 diff 就无法发现它是否被删除。** `public/protected`、对外 `@Composable` 和 slot 必须全部进入清册。扩展点（D18）不能因为当前场景暂时用不到而遗漏。

### ① 抽规格 SPEC —— 填表，暂不转换

> **如果上游阶段已经产出 `ui_surfaces`、`demo_flows` 的结构化视觉规格和 `design_tokens`，应将其作为本表的初始内容，并回到源码核对和补全，不能从头重复整理，也不能只照抄而不核验。** 如果没有上游规格，则直接从源码整理本表。库自定义组件和需要复刻的 Android Demo 界面使用相同标准，都按本流程逐个界面处理。

按照控件、属性和状态，将 Android 源码**完整整理为规格表**。此时暂不考虑 ArkUI 的具体实现，只忠实记录 Android 源码中的事实和**具体数值**。这样可以把转换过程变成逐项核对：源码中的每一行都必须在最终 ArkUI 实现中得到对应处理，未处理的行就属于差异。

| # | Android 事实（控件/属性/状态 + 具体值，原样记录，暂不转换） | 命中维度 | 计划采用的 ArkUI 实现（由执行者判断，token 在 ② 中确认） |
|---|---|---|---|

- **完整列出，不抽样**：selector 有 4 个 item，就应写 4 行；渐变的每个色标都记录为 `color@offset`；斜体、9-patch 拉伸区域、elevation、动画曲线和时长都要单独记录。
- 无法确定的 Android 默认值应标记为 `?`，留到 ② 中 lookup，不能根据经验填写。
- 可配置项（自定义属性、Adapter 公开方法、registerXxxType、reverseLayout 等开关）应单独标记为“扩展点（D18）”，确保 HAR **对外提供等价能力**，而不是写死。

### ② 实现 IMPL —— 完成映射并执行必要的 lookup（不得凭记忆猜测）

逐条将规格实现为 ArkUI。具体映射方案由执行者判断，但**所有精确 token 都必须查询确认**。是否需要查询应根据**符号类型**判断，而不能根据个人把握程度决定：

> **必须查询的内容：** 枚举常量名和合法取值范围、API 方法签名与参数顺序、属性默认值、属性是否存在或已废弃、单位换算系数与基准、形状或裁剪类名、渐变方向枚举与角度基准、ImageFit 对应的 scaleType 语义，以及某属性能否用于 stateStyles。**记忆只能帮助判断需要查询什么，不能代替查询结果。** 同一会话中已经确认过的同一符号可以复用查询结果。

实现原则：**数值按视觉等价方式一一转换**，不能使用近似值、随意取整或省略色标；**完整实现所有状态**；**复杂能力应使用等价方案实现，不能跳过**，例如异形气泡、带撤销按钮的 Snackbar、折叠吸顶、ripple，以及将反射工厂 registerXxxType 转换为 type/builder 注册表；**所有扩展点都要对外暴露**，并保持签名与语义一致。

**资源化 token（不硬编码）：** 先将 Android 的 `colors.xml`、`dimens.xml`、`styles.xml` 和 `values-night/` 转换为 HarmonyOS 资源（`$r('app.color.*')`、float、深色目录），再在代码中引用，并确保深色变体完整（D17）。**ArkUI 中的每个视觉数值都必须能够追溯到规格表中的 Android 源值，不能自行添加没有来源的新值。** 本流程不依赖渲染图进行比较，因此数值可追溯是控制 UI 偏差的重要依据。

### ③ 逐行 diff VERIFY —— 以规格为准逐项核验（核心步骤，不得省略）

回到规格表，**逐行检查** ArkUI 实现。先根据 ArkUI 组件和属性的真实语义，客观说明实现会呈现什么效果，再与规格逐项比较，并为每行记录判定：

- **PASS**：视觉效果等价，并且必须填写**证据**，指向实现中的具体位置、属性或枚举，例如 `linearGradient({angle:45, …3 色标}) @ FooCard.ets:42`。证据应能够说明该行规格的关键数值，例如色标数量、角度、状态分支数量，以及是否设置了 `fontStyle.Italic`。**没有证据的 PASS 应按未核验处理，即视为 FAIL。**
- **行为类项目（D5/D12/D13/D14/D19/D20/D21）的证据必须证明功能实际生效，而不仅是符号存在**：PASS 证据不能只指向“符号定义在某行”，还必须说明完整过程：`事件/状态来源 → 写入哪个 @State/@Link/@Observed → 哪个组件读取该状态 → 如何触发重新渲染或 Canvas redraw()`。如果其中任何环节中断，例如修改普通字段、读取非响应式 getter、回调没有调用方，都应判定为 FAIL，不能记为 PASS。仅有定义不代表功能已经生效。
- **变换和几何项目（D12/D20/D21）的证据必须是把一个变换后的具体输入按原算法算一遍的结果**，说明这个输入按源码应落在哪里、实现实际把它放到了哪里、两者一致。只指向 `.scale()`、`.rotate()`、`.offset()` 或其他符号所在的行，不算证据，应判为 FAIL。换句话说，"实现里写了 crop、写了 rotate" 不能作为裁剪正确的依据，要确认裁剪区域和方向本身算对了。
- 如果该行涉及**视觉语义判断**，例如枚举含义、是否等比缩放、状态优先级、渐变类型或角度基准、默认值，但没有在 ② 中通过 lookup 确认，应先判定为 **FAIL-未证实**，返回 ② 补充查询后才能判定为 PASS。不能用个人判断代替查询结果。
- **FAIL**：立即返回 ② 修复并重新检查，直到判定为 PASS 或确认属于 GAP。不能以“差不多”作为通过标准。
- **GAP**：只有同时满足以下条件时才能记录，否则仍按 FAIL 继续处理：(a) 已通过 lookup 确认平台确实没有等价能力；(b) 已说明尝试过的等价方案及其具体不足；(c) 对于能够通过自绘或组合补齐的视觉能力，例如异形 clipPath、渐变、带按钮的底部提示条，默认不能判定为 GAP，除非查询结果确认连自绘方案也无法实现。不能把能够实现的内容直接归为 GAP。用一个内置控件替代源码中的自绘控件（例如用系统 Slider 替代自绘滚轮、用普通列表替代自定义绘制的列表），即使行为相近，也属于简化，不是 GAP，除非确认连自绘也做不到。判断一项缺失是否"次要"，要看它是否改变用户能做的操作或最终产出的结果：会改变的不算次要，不能用"功能等价""交互方式不同"一句带过；缺少手势结束后的归位、让操作结果不同的步骤，都属于功能缺失，不是外观或动画差异。

> diff 不是简单查看整体效果，而是根据规格逐行核对，并为每行保留证据。判定标准直接使用第二节中实际涉及的维度；第四节仅用于落盘前的最终检查，不另设一套标准。

### ④ 落盘 GAP —— 完成自检并如实记录

对照第四节的自检清单逐项确认。③ 中判定为 GAP 的项目，以及无法通过自检的项目，应按第五节要求写入 `.ohos-adaptation` 适配报告。**③ 中“规格⇄实现⇄证据”的核对记录和覆盖矩阵必须一并写入文件，不能只在对话中说明。**

## 四、每界面自检清单（实现后逐项确认；只检查实际涉及的维度；未通过项写入第五节）

> 这是**唯一的正式检查清单**，③ 中的逐行 diff 直接使用它。每项都不能根据整体印象判断，必须列出本界面的具体实例作为证据，格式和判定要求见下方。无法提供实例时，应视为未通过。
>
> D1–D21 的编号和含义以第二节为准，检查表和报告必须直接套用这套定义，不能自己另写一套同名编号（例如把 D20 当成“多语言”）。编号相同但含义不同的清单，等于没有按本流程检查。

- [ ] **流程完整执行**：⓪ 清册逐项有去向 → ① 抽规格 → ② 完成必要的 lookup → ③ 逐行 diff（每行有判定和证据，FAIL 已修复）→ ④ 落盘。
- [ ] **逐项检查第二节中实际涉及的每个维度（D1–D21）**。每项都要指出本界面中该维度最容易出现问题的具体控件或状态作为证据，例如“XX 按钮 disabled 状态：规格第 N 行 → 实现 `Foo.ets:M`”。无法提供实例时视为未通过。**行为类维度（D5/D12/D13/D14/D19/D20/D21）的证据必须包含完整过程，与 ③ 中的要求一致，不能只说明符号位于某行。**
- [ ] **再次检查常见遗漏**：斜体没有被字重设置覆盖（D8），渐变没有简化为纯色（D7），异形没有简化为矩形（D6）；自绘或变换没有被简化为文字，也没有使用不等价的声明式修饰符代替变换模型（D20）；运行时视觉确实由响应式状态驱动（D19）；函数行为与名称一致，并且不存在没有标记词的虚假实现（D21）。
- [ ] **已完成 lookup**：所有具体枚举、API 和默认值都经过查询确认，没有仅凭记忆编写；无法确认的项目已写入差距清单。

## 五、诚实差距报告（落盘要求）

产物写入 `.ohos-adaptation`，并遵循当前 agent 的产物约定。**以下两项必须写入文件：**

1. **逐项覆盖矩阵**（即 ③ 中的核对记录，**无条件必须产出**）：规格表或清册中的**每一行**都要在矩阵中有对应记录，每行包含“证据/差异”列，最终判定只能记录为 **PASS / GAP**。FAIL 必须先修复为 PASS，或在满足条件后转为 GAP。需要进行**双向核验**：① 规格表中的每一行在矩阵中都有对应项；② ⓪ 清册中的每一项都进入规格表，或有明确的无视觉影响说明。**矩阵行数必须大于或等于规格表行数**，扩展点和 Adapter 公开方法必须逐项对应且数量相等，缺少任何一项都应记为 GAP。
2. **差距清单**（可以为空，但必须是在完成逐行 diff 后确认没有差距，不能因为未核对而为空）：每条差距都要说明 ① 对应规格表中的哪一行和哪个维度；② ArkUI 当前采用了什么等价实现，与原效果存在哪些具体差异，以及近似程度；③ 如果完全无法还原，需要说明具体差异和影响范围。

**不得使用“基本一致”或“完全一致”掩盖实际差距。** 如实记录差距，比未说明地简化或遗漏控件更重要。
