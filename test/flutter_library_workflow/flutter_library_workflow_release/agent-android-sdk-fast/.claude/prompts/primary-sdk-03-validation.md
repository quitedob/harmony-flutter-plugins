# 编码校验与修复（Android → HarmonyOS HAR）

你负责独立检查生成的 HarmonyOS HAR 和 Demo。根据 Android 源码、HarmonyOS 实际代码和重新构建的结果判断。

发现可以修复的问题时，直接修改 `ohos_hardemo/library/` 或 `ohos_hardemo/entry/`，重新编译并再次检查。不要只记录问题而不处理。

## 输入和输出

开始前读取：

- `.ohos-adaptation/02-implementation-report.md`
- Android 库、资源文件及 Demo/sample 源码
- `ohos_hardemo/library/`
- `ohos_hardemo/entry/`

最终写入：

- `.ohos-adaptation/03-validation-report.md`

## 校验范围

### 1. 功能对齐

以 Android 源码为最终依据，全量检查并复核实现：
- 按功能模块是否完成完整迁移
- public/protected API、常量、枚举、Builder、回调、监听器和注册入口是否遗漏。
- 名称、参数、返回值、同步/异步方式、默认值、错误处理和副作用是否合理对应。
- 配置项是否能真实传到实现端并生效，跨页面或跨模块参数的键名和类型是否一致。
- 回调和注册入口是否有真实调用链路。
- native 相关能力是否有 NAPI 配置、注册、ArkTS 封装和真实实现。
- 坐标、矩阵、裁剪、缩放、像素映射等算法是否核对过单位、原点、轴心、方向和变换顺序。

以下情况必须判为问题并优先修复：空实现、固定返回值、测试数据、只打印日志、只在 Demo 中绕过 library 实现、删除 native 后用简单 ArkTS 代替、符号存在但行为不符合名称。

类不要求保持 Android 的结构，但对应能力必须在 HarmonyOS 实现，并被使用。

涉及 JNI、C、C++ 或 so 时，检查 NAPI 构建配置、注册代码、ArkTS 封装和 native 实现是否完整。

静态检查能够确定的问题必须在本阶段确认或修复。

### 2. UI 对齐

使用 `android-to-harmonyos-ui-mapping` 重新检查库组件，重点确认：

- Android UI 面是否都有 ArkUI 对应实现。
- 自定义 View/ViewGroup、Compose 组件和界面、`onDraw`、`onMeasure`、`onTouch` 是否迁移为真实使用的 ArkUI 自绘或等价组件。
- selector 状态、自定义 attr、Adapter 方法、Compose 参数、slot、状态和回调是否完整。
- 结构、尺寸、颜色、字体、圆角、描边、阴影、渐变、图片缩放、动画、弹窗、深色资源等视觉值是否能追溯到 Android 源码或资源。
- 运行时会变化的 UI 是否存在完整通路：事件或数据来源 → 响应式状态或 Canvas 重绘 → 组件读取 → 界面变化。

只声明状态但没有写入或读取关系，或者只修改普通字段但没有触发界面更新，都需要修复。

### 3. Demo 覆盖

检查 Demo 是否能作为真实验收入口：

- 每个对外 API 都有可操作入口。
- Demo 调用进入 `library` 的真实实现，界面展示真实返回值、状态变化、回调结果或副作用。
- Android 自带 Demo 的页面、导航、参数和结果回传在 HarmonyOS Demo 中可到达、可执行。
- 运行时权限同时有 `module.json5` 声明和动态申请。
- 平台确实不支持的能力在 Demo 中明确提示“不支持”。

Demo 中自行生成结果、绕过 library、只写日志或只做静态展示，都不能算通过。

### 4. 状态更新和自绘检查

对运行时会变化的 UI 配置属性，确认存在完整更新过程：

`事件或数据来源 → 更新的响应式状态或 Canvas 重绘 → 读取状态的组件 → 最终界面变化`

只声明 `@State` 但没有真实写入或读取关系，不能判断为通过。只修改普通字段但没有触发重新渲染、没有接入 @Watch 使 Canvas 重绘等，应直接修复。

对自定义 View 和复杂几何功能，确认：

- 自绘组件有真实使用位置
- Canvas 绘制、测量和触摸处理参与实际功能
- Matrix、pivot、裁剪和像素映射由能够表达原算法的变换模型实现
- 通用 `.scale()`、`.rotate()`、`.translate()` 没有被用于替代无法表达的复杂变换

## 修复和复查

发现问题时直接修复，常见问题如下：

- API 核心功能缺失
- 固定返回、空实现或模拟数据
- native 接入不完整
- UI 面缺失或视觉值不一致
- 响应式编程错误，状态变化没有触发界面更新
- 自绘组件没有使用或几何算法错误
- Demo 没有调用 library 的真实实现
- 页面导航、结果回传或权限流程不完整
- HAR 或 HAP 编译失败
- 源码里有、但被标注为“未实现 / 暂未实现 / 简化 / 用其他控件替代 / 功能受限 / TODO / 后续”的功能
- 其他检查出的问题

不得通过删除功能、写死可配置项、空实现或跳过模块来解决问题。复杂、工作量大、耗时都不是保留差距的理由；只有查证平台确实做不到时才能保留，并实现最接近的可用替代。也不能以“功能等价”“交互方式不同”为由跳过某项行为，或把会改变用户可执行操作或最终结果的缺失当作次要差异；这类应判为需要修复，而不是写入报告了事。

## 重新编译

修复后，在 `ohos_hardemo/` 下重新编译。

## 输出报告

写入 `.ohos-adaptation/03-validation-report.md`，使用中文，字数尽量少，简短说明：

1. 独立检查的源码和产物范围
2. 发现的遗漏或错误
3. 功能检查结果和证据
4. UI 检查结果，包括 D1-D21、状态更新、自绘组件和资源引用
5. Demo 检查结果，包括真实 library 调用、可见结果、导航、回传和权限
6. 本阶段修复的问题、修改位置和复查结果
7. 独立得出的最终结论
