# sdk-case-review - SDK 测试用例评审 Skill

## 概述

`sdk-case-review` Skill 专门用于评审 SDK 测试用例（阶段产物）的质量和规范性。

**适用范围**：
- SDK 测试用例评审
- 评审对象：`04-test-cases.json`、`01-test-points.json`（内含 `modules[].featurePoints[]` 功能点）

> **绑定模型**：模块 1──N 功能点 1──1 测试用例（用例 `id == featurePointId`）。一个功能点可由多个协同 API 实现；API 是用例级元数据 `coveredApis:{android:[],harmony:[]}`，不再逐 API 拆用例。

---

## 输入参数

| 参数 | 必填 | 说明 |
|------|------|------|
| `review_type` | 是 | 固定为 `test_cases` |
| `input_files` | 是 | 输入文件路径数组：`[04-test-cases.json, 01-test-points.json, 01-test-analysis-report.md]` |
| `output_dir` | 否 | 输出目录（默认为 `.ohos-adaptation`） |

---

## 输出文件

| 文件 | 说明 |
|------|------|
| `{output_dir}/03-case-review-report.md` | 评审报告 Markdown |

> **注意**：评审结果仅输出 Markdown 格式报告，不生成 JSON 文件。

---

## 评审维度

| 维度 | 权重 | 通过线 | 评审重点 |
|------|------|--------|----------|
| 覆盖率 | 35% | ≥85 分 | 功能模块覆盖、功能点覆盖（1:1）、Android API 集合覆盖、测试类型覆盖 |
| 可执行性 | 30% | ≥80 分 | 步骤清晰性、操作可行性、前置/后置条件明确 |
| 可判定性 | 20% | ≥80 分 | 预期结果明确、验证点具体、无歧义 |
| 规范性 | 15% | ≥75 分 | 测试标题规范、测试步骤规范、coveredApis/featurePointId 完整、用例 ID 规范 |

**通过标准**：总体≥80 分 且 各维度均达标

## 执行步骤

### 步骤 1：读取评审材料

读取以下文件：
- `.ohos-adaptation/04-test-cases.json` - 测试用例 JSON
- `.ohos-adaptation/01-test-points.json` - 功能点汇总 JSON（`modules[].featurePoints[]`）
- `.ohos-adaptation/01-test-analysis-report.md` - 测试分析报告

### 步骤 2：执行两方比对校验

**校验内容**：
1. 模块数校验：功能点 JSON = 测试用例 JSON
2. 用例总数校验：功能点数 = 用例数（1:1）
3. 级别分布校验：L0/L1/L2 各级别数量一致
4. 模块级用例数校验：每个模块的功能点数 = 用例数
5. 功能点 1:1 绑定校验：功能点 id 集合 == 用例 id 集合；每条用例 `featurePointId == id` 且指向有效功能点；用例 `coveredApis.android` 与对应功能点一致

**校验失败处理**：任何一项校验失败，评审直接判定为**不通过**。

### 步骤 3：执行覆盖率评审

**检查清单**：
- [ ] 所有功能模块都有测试用例
- [ ] 所有功能点都有用例对应（1:1，功能点 id 集合 == 用例 id 集合）
- [ ] **Android API 集合覆盖（聚合校验）**：待覆盖 Android API 并集 ⊆ ∪(各用例 `coveredApis.android`)。一条用例可覆盖多个 API，不要求逐 API 一条用例
- [ ] 正常流程、异常流程、边界条件测试用例完整
- [ ] L0-L2 级别分布合理（L0:≤30%, L1:≤40%, L2:剩余比例）

### 步骤 4：执行可执行性评审

**检查清单**：
- [ ] 每个测试步骤都是用户可在 UI 上执行的操作
- [ ] 无"调用 XXX 方法"等代码级描述
- [ ] 输入操作指定了具体的输入框和输入内容
- [ ] 点击操作指定了具体的按钮
- [ ] 前置条件是测试执行前可检查的状态
- [ ] 后置条件是测试执行后可恢复的状态

### 步骤 5：执行可判定性评审

**检查清单**：
- [ ] 预期结果具体明确，可判定 pass/fail
- [ ] 无"功能执行正确，结果符合预期"等模糊描述
- [ ] 无"可能"、"大概"、"应该"等不确定词汇
- [ ] 验证点与测试步骤一一对应
- [ ] 用例描述无歧义

### 步骤 6：执行规范性评审

**检查清单**：
- [ ] 测试标题使用黑盒功能视角描述
- [ ] 测试步骤使用纯黑盒描述（点击、输入等 UI 操作）
- [ ] 测试步骤内无 API 名、无 `(API:)` 备注
- [ ] 预期结果使用功能视角描述
- [ ] 每条用例含 `coveredApis:{android:[],harmony:[]}` 与 `featurePointId`
- [ ] 用例 ID 符合规范（`F-01-01` 格式）且 `id == featurePointId`
- [ ] Markdown 表格格式正确
- [ ] JSON 格式有效
- [ ] JSON 与 Markdown 内容一致

### 步骤 7：计算得分和通过状态

### 步骤 8：生成评审报告（Markdown 格式）

> **报告模板**：见 `assets/review-report-template.md`

## 评分标准

### 覆盖率评分（100 分）

| 评审项 | 分值 | 扣分规则 |
|--------|------|----------|
| 功能模块覆盖 | 25 分 | 每遗漏 1 个模块扣 10 分 |
| 功能点覆盖（1:1） | 25 分 | 每遗漏 1 个功能点扣 5 分（功能点 id 集合与用例 id 集合不一致即扣分） |
| Android API 集合覆盖 | 25 分 | 聚合校验：待覆盖 API 并集 ⊆ ∪(各用例 coveredApis.android)，每遗漏 1 个 API 扣 5 分（不按逐 API 一条用例评分） |
| 测试类型覆盖 | 15 分 | 每缺少一类测试扣 5 分 |
| 级别分布合理 | 10 分 | 分布严重偏离扣 5 分 |

### 可执行性评分（100 分）

| 评审项 | 分值 | 扣分规则 |
|--------|------|----------|
| 步骤清晰性 | 30 分 | 每处不清晰扣 5 分 |
| 操作可行性 | 30 分 | 每处非 UI 操作扣 10 分 |
| 前置条件明确 | 20 分 | 每处模糊扣 5 分 |
| 后置条件明确 | 20 分 | 每处模糊扣 5 分 |

### 可判定性评分（100 分）

| 评审项 | 分值 | 扣分规则 |
|--------|------|----------|
| 预期结果明确 | 40 分 | 每处模糊扣 5 分 |
| 验证点具体 | 35 分 | 每处模糊扣 5 分 |
| 无歧义 | 25 分 | 每处歧义扣 10 分 |

### 规范性评分（100 分）

| 评审项 | 分值 | 扣分规则 |
|--------|------|----------|
| 测试标题规范 | 20 分 | 每处 API 视角描述扣 5 分 |
| 测试步骤规范 | 25 分 | 每处直接 API 调用扣 10 分；步骤内出现 API 名或 `(API:)` 备注每处扣 5 分 |
| 预期结果规范 | 20 分 | 每处 API 视角描述扣 5 分 |
| coveredApis/featurePointId 完整 | 15 分 | 每条用例缺 `coveredApis` 或 `featurePointId` 扣 5 分 |
| 用例 ID 规范 | 10 分 | 非 `F-01-01` 格式或 `id != featurePointId` 每处扣 5 分 |
| 模板遵循 | 10 分 | 章节结构/表格格式不符每处扣 5 分 |

## 通过标准

| 维度 | 通过分数线 |
|------|------------|
| 覆盖率 | ≥ 85 分 |
| 可执行性 | ≥ 80 分 |
| 可判定性 | ≥ 80 分 |
| 规范性 | ≥ 75 分 |
| **总体** | **≥ 80 分** 且各维度均达标 |

## 评审结论

| 评审结论 | 条件 |
|---------|------|
| **通过** | 总体≥80 分 且 各维度均达标 且 两方比对 100% 一致 |
| **有条件通过** | 总体≥80 分 但有个别维度未达标，需完成必须修订项 |
| **不通过** | 总体<80 分 或 两方比对不一致 或 关键维度缺失 |

---

## 校验失败处理

**两方比对校验失败**：
- 任何一项校验失败，评审直接判定为**不通过**
- 在评审报告中明确列出不一致的详情
- 要求重新生成上一阶段的产物
