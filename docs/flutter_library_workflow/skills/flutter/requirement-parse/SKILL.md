# requirement-parse - PRD 需求解析工具

## 概述

`requirement-parse` Skill 是一个用于解析 Flutter/RN/原生库鸿蒙化适配 PRD（产品需求文档）并自动提取结构化信息的工具。

**适用范围**：
- Flutter 插件/库的鸿蒙化适配需求解析
- React Native 模块的鸿蒙化适配需求解析
- 原生 Android/iOS 库的鸿蒙化适配需求解析

---

## 输入参数

| 参数 | 必填 | 说明 |
|------|------|------|
| `prd_path` | 是 | PRD 文件路径（支持 .md, .xlsx, .json） |
| `output_dir` | 否 | 输出目录（默认为 `.ohos-adaptation`） |

---

## 输出文件

| 文件 | 说明 |
|------|------|
| `{output_dir}/00-requirement.json` | 结构化需求数据（JSON Schema 定义） |
| `{output_dir}/00-requirement-report.md` | 需求解析报告（人类可读 Markdown） |

---

## 解析内容

**提取的字段**：
- **基本信息**：插件名称、版本、仓库地址、许可证、已支持平台、插件类型
- **功能模块**：模块编号、模块名称、功能描述、优先级
- **API 接口**：方法签名、所属模块、参数列表、返回值类型
- **权限需求**：权限名称、平台声明、用途说明
- **使用场景**：目标用户、使用场景列表

---

## 执行步骤

### 步骤 1：读取 PRD 文件

**操作**：
1. 检查文件是否存在
2. 读取文件内容
3. 检测文件格式（Markdown/Excel/JSON）

**检查清单**：
- [ ] PRD 文件存在
- [ ] 文件可读
- [ ] 编码为 UTF-8

### 步骤 2：解析各章节内容

#### 2.1 基本信息解析

**目标章节**：第 1 章"插件概述"

**提取字段**：
- 插件名称、版本、仓库地址、许可证、已支持平台

#### 2.2 功能模块解析

**目标章节**：第 2 章"功能模块划分"

**提取字段**：
- 模块编号、模块名称、功能描述、优先级

#### 2.3 API 接口解析

**目标章节**：第 3 章"API 规格"

**提取字段**：
- API 名称、方法签名、所属模块、参数、返回值

#### 2.4 权限需求解析

**目标章节**：第 6 章"权限需求"（如有）

**提取字段**：
- 权限名称、Android 声明、iOS 声明、用途

#### 2.5 使用场景解析

**目标章节**：第 1 章"典型使用场景"

**提取字段**：
- 目标用户、使用场景列表

### 步骤 3：插件类型识别

根据功能描述关键词自动识别插件类型：

| 类型 | 关键词 | 示例 |
|------|--------|------|
| `platform_interaction` | 屏幕、常亮、相机、蓝牙、存储、传感器、系统 API | flu_wake_lock |
| `business_feature` | 支付、地图、推送、OCR、分享 | 支付 SDK |
| `ui_component` | 组件、UI、渲染、Widget | UI 组件库 |
| `architecture_tool` | 工具、封装、通用、helper | 工具类库 |
| `ffi` | FFI、动态库、.so、.dll | FFI 插件 |

### 步骤 4：生成结构化 JSON

**Schema 验证**：必须包含的顶层字段：
- `$schema`：Schema 声明
- `pluginInfo`：插件基本信息
- `modules`：功能模块数组
- `apis`：API 接口数组
- `permissions`：权限需求数组（可为空）
- `usageScenarios`：使用场景

**文件路径**：`{output_dir}/00-requirement.json`

**检查清单**：
- [ ] JSON 格式有效
- [ ] 所有必填字段都存在
- [ ] 模块编号格式正确（F-XX）
- [ ] API 签名精确保留
- [ ] Schema 声明正确

### 步骤 5：生成需求解析报告 MD

**报告结构**：
1. 插件基本信息（表格）
2. 功能模块划分（表格 + 详细说明）
3. API 接口规格（表格）
4. 权限要求（表格）
5. 使用场景（列表）
6. 鸿蒙化适配关键点
7. 测试范围
8. 测试级别定义

**文件路径**：`{output_dir}/00-requirement-report.md`

**检查清单**：
- [ ] 所有章节都生成
- [ ] 表格格式正确
- [ ] API 信息与 JSON 一致
- [ ] 模块信息与 JSON 一致

### 步骤 6：验证文件完整性

**验证内容**：
- [ ] `00-requirement.json` 存在且非空
- [ ] `00-requirement-report.md` 存在且非空
- [ ] 两个文件内容一致

**验证失败处理**：任何文件缺失都必须补充生成，不允许跳过。

---

## 边界情况处理

| 情况 | 处理方式 |
|------|---------|
| PRD 章节缺失（功能模块） | 从 API 规格章节反推模块 |
| PRD 章节缺失（API 规格） | 返回空数组，记录警告 |
| PRD 章节缺失（权限需求） | 返回空数组（默认无权限） |
| PRD 章节缺失（使用场景） | 从插件简介推断 |
| 字段值不确定 | 使用 `null` 标记 |
| 字段值模糊 | 保持原文，不猜测 |
| 模块编号格式不统一 | 统一转换为 F-XX 格式 |
| API 签名格式不一致 | 保持原文，不做修改 |

---

## 质量要求

- **完整性**：所有功能模块和 API 必须 100% 提取
- **准确性**：方法签名、参数类型必须与 PRD 原文一致
- **结构化**：JSON 格式必须规范
- **可追溯**：每个 API 必须能追溯到所属模块
- **强制性**：JSON 和 MD 两个文件都必须生成

---

## 质量检查清单

生成完成前，必须执行以下检查：
- [ ] 所有功能模块都已提取（无遗漏）
- [ ] 所有 API 都已提取并关联到模块
- [ ] 方法签名与 PRD 原文一致
- [ ] JSON 和 MD 内容一致
- [ ] 两个文件都已生成
