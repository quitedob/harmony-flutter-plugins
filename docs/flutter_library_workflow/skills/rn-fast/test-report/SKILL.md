# test-report - 测试报告 Skill

## 概述

`test-report` Skill 用于汇总端到端测试全流程（测试设计→用例评审→Demo生成→黑盒验证）的结果并生成测试报告。

**适用范围**：
- 测试设计全流程结束后生成总结报告
- 输入：测试点、测试用例、评审报告、Demo生成、黑盒验证数据
- 输出：测试报告（Markdown）

---

## 输出文件

| 文件 | 说明 |
|------|------|
| `{output_dir}/07-test-report.md` | 测试报告（Markdown 格式） |

---

### 项目背景

报告开头需包含项目背景介绍，说明插件的来源、功能和适配目标。

**格式**：

```
# 测试报告

**测试插件**: {plugin_name}
**插件类型**: {plugin_type}（UI组件类/后台服务类/平台交互类/工具类）
**Flutter 功能描述**: {从测试分析报告中提取插件功能简介}
**报告日期**: {YYYY-MM-DD}

## 一、项目背景
```

### 四、测试设计结果分析

对测试设计阶段产出数据进行全面分析。**必须使用表格展示数据，每条数据后附总结描述。**

#### 4.1 测试点统计

**格式**：
```
| 模块 | 测试点数 | L0 | L1 | L2 |
|------|----------|----|----|----|
| F01 模块名 | N | N | N | N |
| F02 模块名 | N | N | N | N |
| 合计 | N | N | N | N |

**总结**：[例如"共 X 个测试点，其中核心模块 F01 占比最高（Y 个，Z%），L0 级用例集中在核心接口验证，级别分布合理/需调整。"]
```

#### 4.2 测试点对功能模块覆盖

从 `01-test-points.json` 和 `04-test-cases.json` 中提取各模块数据，逐一对比。

**格式**：
```
| 模块 | 测试点数 | 用例数 | 覆盖率 | 覆盖状态 |
|------|----------|--------|--------|----------|
| F01 模块名 | N | N | XX% | 全覆盖 |
| F02 模块名 | N | 0 | 0% | 未覆盖 |
| 合计 | N | N | XX% | |

**总结**：[例如"X 个模块中 Y 个全覆盖，覆盖率 Z%。F-XX 模块用例数少于测试点，建议补充 Y 条用例。"]
```

**覆盖状态判定**：
- 全覆盖：测试点数 = 用例数
- 部分覆盖：用例数 > 0 但 < 测试点数
- 未覆盖：用例数 = 0

#### 4.3 测试点对 API 覆盖

从测试分析报告中提取 API 列表，比对测试点是否覆盖。

**格式**：
```
| 指标 | 数值 |
|------|------|
| 总 API 数 | N |
| 已覆盖 API | N（XX%） |
| 未覆盖 API | N（XX%） |

未覆盖 API 列表：
- methodName1（模块名）
- methodName2（模块名）

**总结**：[例如"X 个 API 中已覆盖 Y 个，覆盖率 Z%。未覆盖的 API 共 N 个，其中 F-XX 模块的 methodName 为核心接口，建议补充对应测试用例。"]
```

#### 4.4 测试点→用例转化

**格式**：
```
| 指标 | 数值 |
|------|------|
| 测试点总数 | N |
| 测试用例总数 | N |
| 转化率 | XX% |

**总结**：[例如"共 X 个测试点，已转化为 Y 条测试用例，转化率 Z%。说明测试设计覆盖率良好/不足，其中 X 个测试点未转化为用例。"]
```

#### 4.5 用例对测试点覆盖

验证每条测试用例是否对应到测试点，确保编号一致。

**格式**：
```
| 指标 | 数值 |
|------|------|
| 测试用例总数 | N |
| 已关联测试点用例 | N（XX%） |
| 未关联测试点用例 | N（XX%） |

**总结**：[例如"N 条测试用例中，Y 条与测试点编号完全对应（XX%），剩余 N 条为补充用例/或存在编号不一致需核查。"]
```

#### 4.6 级别分布

**格式**：
```
| 级别 | 数量 | 占比 |
|------|------|------|
| L0 | N | XX% |
| L1 | N | XX% |
| L2 | N | XX% |

**总结**：[例如"级别分布合理/L0 占比偏高，L0 占比 XX%（建议 25%-50%），说明测试重点在核心功能/需调整分布。"]
```

#### 4.7 自动化可行性分析

分析测试用例中可自动化 vs 需手工验证的部分。

**可自动化测试项特征**：
- UI 操作类：点击、输入、选择、观察等可脚本化的操作
- 逻辑验证：API 功能正确性、边界条件、异常处理

**需手工验证项特征**：
- UI 视觉效果：颜色、布局、动画、字体
- 用户交互体验：手势流畅度、响应速度主观感受
- 第三方服务集成：依赖外部服务的完整流程（如 OAuth 授权）
- 设备能力：摄像头、传感器、GPS（需真机手工操作）

**格式**：
```
| 类型 | 用例数 | 占比 |
|------|--------|------|
| 可自动化 | N | XX% |
| 需手工验证 | N | XX% |

**总结**：[例如"X 个用例中 Y 个可自动化（Z%），剩余 N 个需手工验证。手工验证主要集中在 UI 视觉效果（X 个）和第三方服务集成（Y 个）。"]
```

#### 4.8 测试设计结论

基于以上数据分析，给出明确结论：
- 测试点是否充分覆盖功能模块和 API
- 测试用例是否完整转化所有测试点
- 自动化可行性评估

**格式**：
```
**测试设计结论**：[1-2 段文字总结]
- 测试覆盖：[覆盖率是否满足要求]
- 用例质量：[用例是否充分、是否有遗漏]
- 自动化可行性：[可自动化比例是否合理，哪些必须手工测试]
- 建议：[需要补充的测试项]
```

### 五、测试结果分析

基于黑盒验证数据。如缺少黑盒验证数据，说明原因。**必须使用表格展示数据，每条数据后附总结描述。**

**格式**：
```
| 指标 | 数值 |
|------|------|
| 总执行用例 | N |
| 通过 | N（XX%） |
| 失败 | N（XX%） |
| 阻塞 | N（XX%） |

**总结**：[例如"共执行 X 个用例，通过率 Y%。失败 Z 个主要集中在 XXX 模块，建议优先修复。"]
```

各模块通过率表格：
```
| 模块 | 用例数 | 通过 | 失败 | 通过率 |
|------|--------|------|------|--------|
| F01  | N | N | N | XX% |
| F02  | N | N | N | XX% |

**总结**：[例如"F01 模块通过率最高（XX%），F02 通过率较低（YY%），主要原因为 ZZZ。"]
```

失败用例明细表格：
```
| 用例 ID | 标题 | 模块 | 失败原因 |
|---------|------|------|----------|
| F01-001 | XXX | F01 | 描述 |

**总结**：[例如"共 X 个失败用例，其中 Y 个为网络异常导致的偶发失败，Z 个为功能缺陷需修复。"]
```

**黑盒验证结论**：
- **黑盒验证中任何用例失败，结论即为"不通过"**，不存在"部分通过"结论
- 通过率 100% → 通过
- 通过率 <100% → 不通过（列出失败原因和建议）
- 如黑盒验证数据缺失 → 说明原因，标注"黑盒验证未执行"

### 六、质量评估

```
| 评估维度 | 得分 | 说明 |
|----------|------|------|
| 测试设计质量 | XX/100 | 来自用例评审得分 |
| 测试执行质量 | XX/100 | 来自黑盒验证通过率 |

**总结**：
- **测试设计质量**：[例如"用例评审得分 XX/100，覆盖率、可执行性、规范性均达标/存在不足"]
- **测试执行质量**：[例如"黑盒验证通过率 XX%，全部通过/存在 N 个失败用例"]
- **综合结论**：[例如"测试设计质量良好，执行因设备环境问题存在失败用例，建议修复后复测"]
```

### 七、测试结论与建议

#### 测试结论

**⚠️ 结论判定规则（强制）**：
- 黑盒验证存在失败用例 → **不通过**（无论其他指标如何）
- 所有黑盒验证通过 + 覆盖率 ≥85% + 用例评审通过 → **通过**
- 其他情况 → **有条件通过**

| 结论 | 条件 |
|------|------|
| **通过** | 黑盒验证 100% 通过，测试覆盖率 ≥85%，用例评审通过，核心功能可用 |
| **有条件通过** | 黑盒验证未执行或有个别失败，测试覆盖率 ≥70%，核心功能基本可用 |
| **不通过** | 黑盒验证存在失败用例，或 测试覆盖率 <70%，或 核心功能不可用 |

#### 建议

1. **改进建议**：覆盖率提升、用例优化等
2. **后续行动项**：下一步需要做的工作

#### 需要手工补充验证的用例

列出所有需手工验证的用例，说明原因和验证建议。

**格式**：
```
| 用例 ID | 标题 | 模块 | 手工验证原因 | 验证建议 |
|---------|------|------|-------------|---------|
| F01-003 | XXX | F01 | UI 视觉效果验证 | 人工检查颜色、布局是否符合设计 |
| F02-005 | YYY | F02 | 第三方服务集成 | 需手动完成 OAuth 授权流程 |

**合计**：N 个用例需手工验证，占全部用例的 XX%。
```

#### 黑盒验证失败用例明细

列出所有失败用例，说明失败原因和后续处理建议。

**格式**：
```
| 用例 ID | 标题 | 模块 | 失败原因 | 处理建议 |
|---------|------|------|----------|---------|
| F01-001 | XXX | F01 | 描述失败原因 | 重新执行/修复后重测 |
```

## 二、数据呈现规则

所有涉及数据的章节必须使用图表化呈现，并在数据后给出总结描述。

### 2.1 图表呈现原则

- **优先使用表格**：模块对比、级别分布、阶段汇总等结构化数据用 Markdown 表格
- **数据后必须跟总结**：每个数据表/图表后必须有 1-3 句文字总结，说明关键发现和结论，禁止只列数据不分析

### 2.2 禁止事项

- 禁止只列出数据表格而没有分析描述
- 禁止使用模糊总结（如"数据如上所示"），总结必须包含明确的判断和洞察
- 禁止数据缺失时留空表格，必须标注"数据不可用"并说明原因

### 2.3 总结描述模板

每个数据章节末尾必须有类似格式的总结：

```
[数据表格/图表]

**总结**：[用 1-3 句话说明关键发现，例如"X 个模块中 Y 个全覆盖，覆盖率 Z%，其中 F-XX 模块用例数少于测试点 X 个，建议补充。"]
```

## 三、数据提取规则

### 3.1 从 01-test-points.json 提取

- `summary.totalPoints` → 测试点总数
- `summary.levelDistribution` → 级别分布
- `modules[].moduleCode` + `modules[].moduleName` → 模块列表
- `modules[].points[]` → 各模块测试点

### 3.2 从 04-test-cases.json 提取

- `suite.id` → 插件名称
- `modules[].moduleCode` + `modules[].moduleName` → 模块列表
- `modules[].test_cases[]` → 各模块用例

### 3.3 从 03-case-review-report.md 提取

- 评审结论（通过/有条件通过/不通过）
- 总体得分和四维度得分

### 3.4 从 05-demo-gen.json 提取

- 生成结果（成功/失败）
- Demo 包含的用例页面数

### 3.5 从 06-blackbox-verify.json 提取

- 执行结果
- 通过/失败/阻塞用例数
- 失败用例详情

### 3.6 从 01-test-analysis-report.md 提取

- 插件功能描述（用于项目背景）
- 插件类型
- API 列表

---

## 四、注意事项

1. 部分阶段产物缺失时，对应章节说明"数据不可用"并继续
2. 覆盖率分析必须基于 `01-test-points.json` 和 `04-test-cases.json` 的逐一对比
3. 所有结论需有数据支撑，不主观推断
4. 自动化可行性分析需基于用例实际类型判断
5. **数据呈现**：所有数据章节必须使用表格展示，禁止使用独立的"可视化"列
6. **数据后必须有总结**：禁止只列出数据而不分析，每个数据表后必须有 1-3 句总结描述，包含关键发现和判断
7. **黑盒验证失败判定**：任何失败用例即判定为"不通过"，不使用"部分通过"结论
8. 报告末尾必须包含"需要手工补充验证的用例"和"黑盒验证失败用例明细"两个明细清单
